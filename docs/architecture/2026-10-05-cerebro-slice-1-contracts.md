## Identity, authority and approvals

Company identity uses the existing `OrganizationId`; conversation, session, agent, run, event, operation, principal, delegation and digest IDs retain their branded meanings. A stable request uses the existing event ID; a new engine attempt must not allocate a new request or run identity. The coordinator derives context from verified credentials and current grants, never from client-supplied claims. Deadlines and caller signals limit waiting; Effect interruption must also reach vendor invocation contexts and abort signals. Neither proves a remote write did not happen.

`AuthorityRequest` carries current context, address, action/resource, pinned agent and optional model/registered tool. Enforcement intersects current actor or delegation, represented principal, pinned agent, enabled models and tools, company/content grants and connector restrictions. Recheck before **each physical** model request, retry, compaction call and tool dispatch, after approval waits and before receipt/history reads. Denial is decision data from `evaluate`; `require` converts it to `Denied`. Unavailable authority fails closed. Fakes provide scripted allow/deny/unavailability; they do not implement production policy.

The existing `Approval` remains untouched. The proposed `BoundApproval` adds required `runId` and `connectorFingerprint`; corresponding `BoundInvocation`, `RegisteredTool` and `BoundCapability` require the same fields. A fingerprint is SHA-256 of canonical JSON containing connector registration ID, configured version and configured destination. Normalize destinations when registering connectors; do not use a client destination. Reuse the existing JSON argument digest rules. Matching additionally compares company, agent, operation, tool/version, effect, argument digest, actor, represented principal, delegation, policy version and strict expiry. The approver remains subject to current approval authority; matching alone does not grant authority. Focused tests mutate run, registration, arguments, identity, policy and expiry, and check that version/destination changes change the fingerprint.

## Receipts and durable handoff

Receipt state is `claimed → dispatched → outcome → completed`, with `dispatched → unknown → outcome` for evidence-based reconciliation. No monetary states occur here. Claim compares the full immutable intent, not only the argument digest. Dispatch compares the current revision and yields one winner; repeats return `dispatch:false`. Writes require a matching approval and current authority. Unknown non-idempotent effects block the same intent even under a new occurrence ID until read-only provider evidence resolves it. The unresolved-intent key uses company, run, pinned agent, tool/version, connector fingerprint, effect kind, argument digest, actor, represented principal and delegation identity; it excludes occurrence ID and policy version. A policy update cannot bypass an unresolved effect. Reconciliation never invokes the effect. Completion and confirmed outcomes are immutable. Durable receipt recording after dispatch must run in a host-owned scope despite caller interruption; that adapter behavior is unqualified.

A handoff stores the immutable command intent: address, pinned version, full envelope, canonical input digest, submission mode, stable request/run IDs, revisions, approvals, replacement-stop phase, engine acceptance, acknowledgement and projection revision. This record is a command journal, not a queue competing with Pi's inbox.

The acknowledgement point is **after the official PiHarness submission returns and Cerebro records engine acceptance**. This applies to queued follow-ups as well as active work. The wrapper supplies durable Pi admission and its Lifecycle wake. There is no independent Cerebro `wake-registered` transition, wake timestamp or admission alarm. An acknowledged `queued` receipt means Pi accepted the input into its inbox; accepting only a Cerebro record is insufficient. Production-equivalent flush remains NOT_RUN.

`SessionService.submit` defaults to follow-up. Steer maps to the native steering mode. Replace is a coordinator-owned sequence: persist the replacement intent, call `EngineConversation.stop`, record `replace-stopped`, then call engine submit as a follow-up with the original replacement identity. `EngineConversation.stop` returns affected states; it does not erase conversation history. Unknown remote effects still require reconciliation and must never be marked successfully cancelled.

Replacement is two vendor calls, not an atomic vendor operation. Command retries must compare mode as well as the full input, return an existing accepted receipt before issuing Stop again, and inspect the original Pi operation when acceptance is ambiguous. Otherwise a retry could stop its own replacement or later work. Serialize conflicting human command mutations during the replacement sequence. The later runtime packet must qualify this repair behavior; the fixture does not implement a durable replacement command coordinator.

Recovery boundaries still requiring real crash injection:

1. Command intent committed before Pi acceptance: repair the original stable handoff, without another execution scheduler.
2. Replacement Stop in progress or completed before its marker commits: inspect original operation state before repeating Stop; retain the command's original identity and mode.
3. Pi accepted before Cerebro records acceptance: inspect/reuse the original vendor operation and repair the marker. This also applies to replacement; do not blindly repeat abort-then-submit.
4. Acceptance recorded before acknowledgement: return the same receipt on retry. Pi's own Lifecycle job owns execution recovery.
5. Pi completed before product projection: project canonical output and confirmed tool outcomes without resubmitting.

The command fake checks replacement phase ordering, mode/input conflicts, acceptance before acknowledgement and replay without another Stop. These are contract checks, not host crash qualification. Pi-native follow-up/steering is measured separately. The local functional process-kill probe now permits ninety seconds without HTTP because celld's default cold-alarm discovery scan runs every sixty seconds. It reads the snapshot before blocking waits and requires both saved answers to predate observation. The earlier forty-five-second failure remains in `evidence/native-recovery-45s/`; it ended before the default scan. A separate targeted investigation passed automatic recovery on both 0.6.0 and 0.6.1 and request-triggered resume on 0.6.1. A prior development probe used blocking HTTP waits and is not evidence of alarm-only completion. Production durability, separate idle eviction and the plan's sixty-second performance budget remain unqualified. No Cerebro scheduler is added. Projection must atomically persist canonical output, required confirmed tool outcomes and terminal run state/outbox. No final success is conditional on metering. Network operations remain outside atomic storage transitions.

## Observation schemas and ordering

`DomainSnapshot`, `DomainUpdate` and `Observation` are runtime Effect schemas in `session-service.ts`. Snapshot fields are address, positive pinned agent version, nonnegative durable revision, existing run states, canonical outputs with content dependencies and provenance citations, and required `userMessages`, `approvals`, `tools` and `executions` arrays. A partial snapshot that omits any collection is invalid, including when that collection is empty. A fresh authorized attachment must restore the full product view without replaying old stream frames or submitting work.

`UserMessage` stores accepted event ID, logical run ID, normalized follow-up/steer/replace mode, finite occurrence time and text. The array retains accepted message order; command retries must not duplicate a message. `ApprovalState` stores approval/run/operation identity, finite expiry and pending/allowed/denied/expired/cancelled state. It is a public projection, not a `BoundApproval` permit. Its run/operation identity links to `ToolState`, which contains tool ID/version, read/write effect, authorized JSON arguments, progress/result JSON, source/tool dependencies and requested/waiting/running/succeeded/failed/cancelled/unknown-outcome state. Use JSON `null` when there is no output; omit credentials and private execution context. Dependencies cover arguments and output. Current authority still controls every projection and approval action.

Live updates include `user-message`, approval state changes and complete tool records, using the same `UserMessage`, `ApprovalState` and `ToolState` schemas as snapshots. Other updates remain run state, provisional text, canonical output and citation. Stable event ID, approval ID and operation ID are their upsert keys; a changed approval state replaces its earlier pending state. Each snapshot replaces all canonical collections, including empty collections, so reload/overflow/reconnect cannot resurrect an old pending approval or stale tool result. Canonical state remains separate from provisional text and vendor-private execution state. Tool/citation/output content carries source/tool dependencies; citations retain source ID/version/URI and observation time. Tool arguments and output must be valid canonical JSON.

Every observation has schema version 1, address, nonempty ephemeral epoch, nonnegative sequence and access generation. Snapshots have an attach/overflow/reconnect reason and full domain snapshot. Updates have a domain revision and validated update. Access denial has an explicit revoked/unauthorized reason and contains no protected content.

Proposed ordering rules:

- Allocate durable revision only for committed domain changes. Provisional text uses the most recent durable revision; sequence orders all frames within an epoch. Repeated revision is permitted only for provisional progress, never as a substitute for a missing committed update.
- Attach by subscribing and buffering **before** reading the canonical snapshot, or by an equivalent atomic host operation. Send the snapshot at revision R first; discard buffered committed updates at or below R; emit each later commit in order. A run completing during attachment must appear in the snapshot or following updates.
- Each attachment or resnapshot creates a fresh epoch with sequence 0. The client validates address and access generation before applying any content; it rejects old epochs, old generations and duplicate sequences. On a sequence or durable revision gap, close that observer and obtain a fresh canonical snapshot.
- Overflow replaces the observer buffer with a fresh authorized snapshot and epoch. Never silently drop committed updates and continue. No durable UI chunk log is promised. Canonical outputs replace provisional output by execution identity and deduplicate by answer identity; snapshots replace protected canonical state.
- Revalidate access while active and idle. Before headers, convert `Denied` to HTTP; after headers, emit a validated `access-denied` notice then close. The client invalidates company/session caches, clears protected output, increments its local access generation, drops delayed old-generation frames and stops automatic reconnect. It resumes only after a new explicit authorized attachment. The one-second revocation budget belongs to later acceptance, not a measured S1-0 pass.

## Joined execution and answer identity, coordinator revision 2026-10-07

A `RunId` identifies one admitted logical command. An `ExecutionId` identifies one engine execution, which can answer several commands after native steering. An `AnswerId` identifies its final canonical answer. These are separate branded Cerebro strings. No vendor type enters the contract.

`ExecutionState` contains `executionId` and a nonempty, ordered, unique `runIds` list. The first member is the primary run and remains fixed. Membership can only append before completion. A queued follow-up does not join an execution until Pi places it. A queued steering input joins only when its placed record confirms membership. Each logical run belongs to at most one execution. Snapshots require the `executions` collection, including when empty. Live membership uses the `execution` domain update.

The adapter derives the execution identity from the primary logical run, for example `id.execution("execution:" + primaryRunId)`, and persists membership. It must retain that identity across Pi task handover and recovery. The public Pi mapping fixture at S1-A head `c11e65f6e1f35c6b6def715c575febded114c409` confirms that placed inputs A and B share an answer EntryId while their generation taskId changes. Therefore taskId is not an execution identity. The adapter maps the private answer EntryId to a stable, session-scoped opaque `AnswerId`. It must not derive answer identity independently for each request.

`CanonicalOutput` retains `runId` as its primary run and adds `answerId`, `executionId` and the complete `runIds` membership. `runId` must equal the first member. Snapshot validation rejects missing or duplicate membership, runs in more than one execution, duplicate answers, more than one answer per execution, and output membership that differs from its execution. Outputs are immutable and deduplicate by `answerId`. Provisional text and citation updates carry `executionId` and the primary `runId`. All joined user messages remain separate. The UI renders one assistant answer for the execution after its linked inputs. Reconnect uses the same identities and does not submit work.

`SessionStore.commit` adds `projected-batch` with an anchor `runId` and a nonempty tuple of durable `DomainUpdate` values. The storage adapter validates the entire batch against admitted handoffs before mutation. It atomically commits execution membership, the one canonical answer, confirmed tool outcomes, all linked terminal run states, handoff projection markers and outbox records. Updates keep their order and each consumes one durable revision. Observers receive those records only after commit. No provisional text or citation-only frame enters a durable batch. Validation failure rolls back the whole batch. Exact replay creates no additional output, terminal transition or outbox record; changed final content or membership fails with typed Conflict.

Every linked run reaches completed only after the shared canonical answer and all required confirmed tool outcomes exist. An unknown write outcome blocks successful completion of the whole joined execution. Tools and approvals retain their original logical run and authority bindings. Steering does not widen those grants. Native Stop of any placed member affects all joined pending runs and queued inputs. Queued withdrawal remains specific to that input. The adapter must report every affected logical run, not only the Stop target.

The coordinator contract checks cover snapshot/live identity validation and atomic batch behavior in a contract fake. The independently rerun public Pi fixture proves native membership and Stop mapping. Application steering, crash repair, celld durability and browser behavior require packet and final integration checks. These facts do not convert prior FAIL or NOT_RUN results to PASS.

## Qualified public TanStack API and remaining adapter work

At the proposed pins, use `stream(factory, { hydrate, joinRun })` from `@tanstack/ai-client`. Do not use TanStack `chat`, AI SDK, `StreamDurability`, built-in byte replay, or model/tool client callbacks.
