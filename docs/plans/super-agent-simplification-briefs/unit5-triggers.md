## Why

Today every coordinator event becomes a four-phase durable delivery task that waits on its predecessor, claims a profile version, submits one Pi follow-up, and settles by binding the run's single answer entry to the event. Pi runs one follow-up per turn, so N messages are N turns. After this unit Pi's inbox is the queue, a burst that arrives during a turn runs in the next turn together, replies to external channels are an explicit model decision through one tool, and every channel is an adapter that produces a `Trigger` and registers a `ReplyPort`.

## Decisions

1. Contract. `packages/contracts/src/triggers.ts` replaces `bot-events.ts` and `bot-routing.ts`. `Trigger { version: 2, id, address, ownerPrincipalId, origin, text, reference, reply: ReplyDestination | null, dependencies }`. `TriggerOrigin` is the union web, slack, timer, teamreport, teamnotice as candidate 3 sketches it. The actor is not stored: export `triggerActor(origin): "human" | "routine" | "internal"` (web and slack human, timer routine, team origins internal) and use it everywhere. `triggerId(address, origin)` keeps today's digest scheme and `bot-event:` prefix. `TriggerAdmission { version: 3, kind: "trigger-admission", trigger, routing }` with the routing union automatic, control, local-control; a bare trigger means direct. `ReplyDestination` is `{ kind: "slack", authority, ownerPrincipalId, source }` today. `ReplyPort<D>` has `authorize(destination)` and `deliver({ destination, key, text, store, beforePost })`; `ReplyPorts` is a map by destination kind. The schema filter encodes: web has `reply: null`; a `reference.key` shares the trigger's organization and owner; text limits per origin as today.
2. Runtime module `packages/runtime/src/triggers.ts` replaces `coordinator-events.ts`, `coordinator-event-state.ts`, `coordinator-event-input.ts`, `coordinator-event-scope.ts`, `conversation-event-scope.ts`, and `coordinator-event-access.ts`. It owns: `Receipts` (doc family kind `cerebro.bot-event`, version 3, `migrate` throws for older versions), `Backlog` per conversation (`ids: string[]`, scope conversation, history latest), `MAX_WAITING = 64` counting Pi inbox items plus backlog at `acceptIn`, `admit`, `acceptIn`, `drain`, `drainAll`, `withdraw`, `queuedWeb`, `placement`, `read`, `list`, and the Team entry points `returnEventIn`, `receiveReturn`, `listSubscribedBotSources` with today's semantics. `drain` is single-flight per conversation: while the backlog is non-empty and `scope.gate()` is open, for each id in order re-authorize the owner for delivery (`scope.authorize(trigger, undefined, "deliver")`; a `Denied` removes the id and leaves the receipt, placement reads `withdrawn`), call `native.submit({ type: "input", requestId: id, whenBusy: "followUp", content: inputText(trigger), entry: { kind: "cerebro.trigger", data: { id, channel, operationId? } } })`, then commit the removal from the backlog. End with `trackNativeProgress(pi, { conversations: [nativeId] }, waitUntil)`. `drain` runs from `admit`, from `drainAll` on restore, and from the `cerebro-coordination` job; it returns `"idle" | "waiting"`.
3. `TriggerScope` is `{ native, ownerPrincipalId, requireCurrent, authorize, commit, gate, route?, localAnswer?, routingAccess?, readAccess }` as candidate 3 sketches it. `gate()` is the scope's `advance()`.
4. Publication gate. `ConversationBinding` becomes `{ address, nativeId, agentVersion, refresh: { agentVersion } | null }`; bump the `Bindings` version and reject older versions. `advance()` returns `"open" | "waiting"`: with no refresh and a newer published version, set `refresh`; with a refresh pending, prepare the target profile and in one commit require `nativeDrainIn` (no live run, empty Pi inbox, no live task other than `cerebro.coordinator-reply`), no pending native operations, no pending approvals, no live admission lease, then `configure` and clear `refresh`. Inputs reach Pi only through `drain`, and `drain` only when the gate is open, so no input runs under a stale definition. `releaseEvent`, `advancePublication(eventId)`, and `oldestHeldEventIn` go.
5. Pi settings: `followUpMode: "all"`. Leave `steeringMode` at its default.
6. Replies. `packages/runtime/src/replies.ts` replaces `coordinator-replies.ts`. `Reply` is keyed by trigger id, copies `destination` from the receipt, and keeps today's outbox task (send and retry phases, backoff, `retryAt`, blocked on `Denied` or `NotFound`, the channel store's never-repeat-an-uncertain-post rule) with `deliver` resolved through `ports[destination.kind]`. `enqueueIn` is idempotent by trigger id: the same text returns the record, another text throws `Conflict`. One reply per trigger.
7. The tool `reply_event({ eventId, text })`, callers model, replay safe, registered on the coordinator profile. It reads the receipt, requires `receipt.nativeId === api.conversationId`, returns an error for a trigger with no destination ("the transcript is the reply"), pre-authorizes with the owner context, the dependency check, and `ports[kind].authorize`, records a blocked reply on `Denied` or `NotFound`, and otherwise enqueues inside `api.commit`.
8. The forgotten-reply nudge is a durable follow-up submission, never an `onYield` continuation. In `hook(GenerationTask, { onYield })` for the coordinator conversation: for each submission in `pi.live.run.inputs` whose receipt has a destination, no reply record, and no `submissionByRequest(nativeId, "reply-nudge:<id>")`, call `native.submit({ type: "input", requestId: "reply-nudge:<id>", whenBusy: "followUp", content: "Trigger <id> has no reply yet. Use reply_event, or say in one line why no reply is needed.", entry: { kind: "cerebro.reply-nudge", data: { id } } })` and return `undefined`. Spike first that a `Conversation.submit` from inside the hook commits cleanly; if it deadlocks, enqueue the nudge through `waitUntil` after the hook returns and say so in the report. Hide `cerebro.reply-nudge` items in `pi-harness.ts` `queuedInputs` and `presentedEntry`. In `instruction-cause.ts` map a nudge entry to the nudged trigger's receipt.
9. Instruction cause. Candidates stay the current run's inputs. For each, verify the entry kind and `data.id` against the receipt (digest, nativeId, owner, address). Actor comes from `triggerActor(receipt.trigger.origin)`. Take the last human, else the last routine; internal never qualifies. Delete the claim checks and the `pi.user` branch.
10. `run-limits.ts` `startsRun` also treats `cerebro.trigger` and `cerebro.reply-nudge` entries as a run start.
11. Adapters. Web: `coordinator-web.ts` builds a web trigger with `reply: null` and routes exact `status`/`stop` to `localAnswer`; replay by operation id is the receipt dedup. Slack: `apps/server/src/session/agent.ts` builds the trigger from the decision receipt with the recorded destination; `createSlackEventReplies` becomes `createSlackReplyPort` and `SessionHostConfiguration.eventReplies` becomes `replyPorts`. Timer: `saved-timer-submit.ts` builds a timer trigger whose `reply` is copied from the reminder origin record, which copies it from the cause trigger's receipt at schedule time; delete `TimerOccurrences` and `resolveFixedReplyOrigin`. Team: `coordinator-report.ts` and `coordinator-event-content.ts` build internal triggers inside the report commit with `reply` copied from the cause trigger's receipt (`humanOperationId` is a trigger id), call `acceptIn`, and the caller runs `drain` after the commit.
12. Subscriptions. `coordinator-subscriptions.ts` keys threads by a generic `threadKey(origin)`: for slack the workspace, channel, and root timestamp; web and other origins have no thread key and never route. `subscribe_work` and `unsubscribe_work` keep their parameters. When `start_team` admits work whose cause trigger has a thread key, subscribe the work to that thread in the same admission commit, so follow-ups in the origin thread reach the Team without a tool call. The coordinator can still unsubscribe.
13. Local answers (`status`, `stop`) keep today's passive entries and enqueue a reply through the same `enqueueIn` when the trigger has a destination.
14. Inspector. `inspection-events.ts` reads receipts plus derived placement plus the reply record; `packages/contracts/src/inspection.ts` `InspectionEvent` gains `channel`, `actor`, `placement`, and keeps `reply`; drop `admission` and `outcome`. The web Inspector renders the new fields.
15. Stop: `triggers.withdraw(native.id)` then the native abort. The snapshot's queued inputs are Pi's inbox projection plus `queuedWeb` for backlog web triggers.
16. Pre-cutover data is not migrated anywhere; version bumps throw on older documents.
